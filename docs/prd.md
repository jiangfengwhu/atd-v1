## 需求歧义与澄清记录

- **[MEDIUM] 点击“分享”按钮由一键复制升级为多途径分享菜单，影响既有单点分享回归用例**: 现有 PostCard 与 PostDetailDialog 点击“分享”按钮会立即触发 POST /api/posts/:id/share 并复制链接，且历史测试 tests/e2e/run-9b961baa.spec.ts 依赖该单次点击行为。升级为类 X.com 多途径分享菜单后，点击“分享”应先展开选项菜单，仅在用户实际选择具体分享动作（复制链接、通过私信发送、复制分享文案、外部/系统分享）时才累加分享数。
  - 澄清建议：按 X.com 标准交互实现：点击分享图标展开多途径菜单，选择具体渠道后执行分享并累加 sharesCount；同时同步更新既有回归脚本 tests/e2e/run-9b961baa.spec.ts 中点击分享后进一步点击“复制链接”的步骤，保持功能验收语义一致。
- **[MEDIUM] “好友”范围界定与站内私信分享对象排序规则**: 当前社区数据模型包含关注关系（user_follows）与私信会话（direct_messages），但没有独立的双向好友申请表。用户反馈提及“站内私信分享给好友”，需明确候选列表包含范围。
  - 澄清建议：私信分享弹窗默认优先展示“最近私信联系人”和“互相关注/已关注用户”（附带关系标签如“最近私信”“互相关注”“已关注”），并支持按昵称搜索站内其他社区用户（自动排除当前登录用户本人且不暴露邮箱），最多支持单次多选 10 位接收人。
- **[LOW] 外部多途径分享在桌面端浏览器不支持 Web Share API 时的降级体验**: 类似 X.com 的多途径分享通常包含复制链接、站内私信、复制分享文案与系统/外部应用分享，但桌面端 Chromium 及部分浏览器不支持 navigator.share。
  - 澄清建议：菜单固定提供“复制链接”、“通过私信发送”、“复制分享文案”和“更多方式分享”四项：当浏览器支持 navigator.share 时调用系统原生分享面板；不支持时优雅降级为复制带摘要的分享链接并给出清晰提示，确保全端可用且无报错。
- **[LOW] 被私信分享的原帖后续被作者删除时的历史消息展示**: 若发帖人在帖子被私信分享后删除该帖，私信双方查看历史会话时需避免出现空白气泡或接口报错。
  - 澄清建议：通过独立的 direct_message_post_shares 关联表记录 message_id 与 post_id，查询私信记录时 LEFT JOIN posts；当原帖已删除时返回 unavailable: true 标记，前端渲染“该动态已被删除或不可查看”的占位卡片。
